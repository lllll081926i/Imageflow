## P1：优先修复

### 1. GIF 缩放在分配全部帧之后才检查尺寸，且不检查输出累计像素

定位：[gif.go:327](/D:/Code/Imageflow/internal/engine/gif.go:327)、[gif.go:407](/D:/Code/Imageflow/internal/engine/gif.go:407)、[resizeutil.go:11](/D:/Code/Imageflow/internal/engine/resizeutil.go:11)。

`transformAnimation` 先执行 `mutation(animation)`，`resizeFrames` 随即对所有帧调用 `imaging.Resize`。直到缩放结束才调用 `output.CheckSize`。输入阶段的 `MaxAnimationPixels` 预算没有用于输出阶段。

触发：导入 500 帧的小尺寸 GIF，再将每帧放大到 8000×8000。输入可以通过当前预算，但仅输出帧的 RGBA 缓冲就需要约 128 GB。分配可能直接导致进程内存耗尽；即使完成缩放，最终的单帧尺寸检查也不会拒绝这些累计像素。超出单边限制的请求同样会先分配、后拒绝。

建议：先计算最终宽高，再用 `animationSize(目标宽, 目标高, 帧数)` 核验完整输出预算，核验通过后才分配任何缩放帧。保留可向调用者返回错误的缩放接口。

证据：静态确认调用顺序与缺失的累计预算；未执行可能耗尽内存的输入。

### 2. 拼图拉伸缩放绕过画布预算，放大后还会错误裁切圆角

定位：[collage.go:342](/D:/Code/Imageflow/internal/engine/collage.go:342)。

`CollageStretch` 直接创建 `w*Scale × h*Scale` 图像，而画布预算只校验了原始画布。界面允许缩放至 5 倍，引擎允许至 8 倍。随后 `roundImage` 对放大后的图像加圆角，最终绘制却只取左上角的单格范围。

触发：8000×8000 的单格画布使用拉伸模式并缩放至 5 倍。最终画布符合 6400 万像素预算，但中间图像变成 40000×40000，仅像素缓冲约 6.4 GB。较小画布也能观察到右侧和下侧圆角被裁掉，且取景偏向左上角。

建议：将单格输出保持为 `w×h`，使用有界的源图取景实现缩放和偏移，最后对单格成品加圆角。所有中间图像也必须经过预算检查。

证据：独立用例中，32×32 的格子在 `Scale=2` 时返回 64×64 中间图像；大内存场景未执行。

### 3. APNG 实际输出后缀与冲突检查后缀不同，跳过策略仍会覆盖文件

定位：[tools.go:1324](/D:/Code/Imageflow/internal/ui/tools.go:1324)、[gif.go:414](/D:/Code/Imageflow/internal/engine/gif.go:414)。

GIF 工具选择 APNG 时，界面使用 `.png` 调用 `outputPathFor`。引擎使用 `ensureExtension(..., "apng")` 将最终路径改成 `.apng`。冲突检查和实际写入针对不同文件。

触发：输出目录已存在 `IFimg00.apng`，但没有 `IFimg00.png`，冲突策略选择“跳过”。任务仍然覆盖现有 APNG。自动重命名策略也无法保护这个实际目标。

建议：在路径预留前统一 APNG 的规范后缀，编码阶段使用已经确认的目标路径。

证据：两帧 GIF 的独立用例确认，跳过策略下预先写入的 `.apng` 文件内容被替换。

### 4. 图标工具绕过冲突策略，会覆盖已有图标及同名输入的结果

定位：[tools_extra.go:316](/D:/Code/Imageflow/internal/ui/tools_extra.go:316)、[settings.go:362](/D:/Code/Imageflow/internal/ui/settings.go:362)、[icons.go:108](/D:/Code/Imageflow/internal/engine/icons.go:108)。

`IconTool.Run` 直接构造 `<源文件名>_icons` 目录，没有调用输出路径预留或冲突检查。`BuildIconSet` 按固定名称写入 `icon-16x16.png`、`icon.ico` 等文件，原子写入仍然会替换原文件。

触发：选择“跳过”后重复生成图标，已有图标仍会被替换。未保留目录结构时，两个不同目录中的同名输入还会写入相同图标目录；并行运行可能生成混合来源的图标集合。

建议：在批处理层按目录预留每套图标，并统一执行跳过、重命名和覆盖策略。相同批次的两个输入不能共享未授权覆盖的目标目录。

证据：独立用例确认，“跳过”策略仍替换现有 `icon-16x16.png`。

## P2：功能与状态错误

### 5. 拼图预览和剪贴板合成实际运行在 UI 主线程

定位：[collage.go:1183](/D:/Code/Imageflow/internal/ui/collage.go:1183)、[collage.go:1206](/D:/Code/Imageflow/internal/ui/collage.go:1206)、[collage.go:1999](/D:/Code/Imageflow/internal/ui/collage.go:1999)。

外层 goroutine 只执行 `win.Update(compose)`。MyGo 当前锁定版本的 `Window.Update` 使用 `postMain` 执行整个回调，因此 `RenderCollage` 的读盘、完整源图解码、色彩转换和缩放均占用主线程。复制还在同一个主线程回调内执行完整尺寸合成与 PNG 编码。

触发：使用多张大型 HEIC、AVIF 或带 ICC 的图片，拖动取景或点击复制。窗口在处理期间不能正常响应。代次检查发生在合成之后，已经过时的排队任务仍会执行完整合成。

建议：后台只处理不可变请求并生成图像或 PNG 数据；`Window.Update` 只核验代次并提交结果。取消或合并已经过时的预览请求。

证据：静态核对项目调用及 MyGo 固定版本 `content.go` 的主线程调度实现。现有无窗口测试走同步分支，未覆盖此问题。

### 6. 批处理中删除或清空输入，会将旧任务结果写入其他图片

定位：[files.go:138](/D:/Code/Imageflow/internal/ui/files.go:138)、[runner.go:51](/D:/Code/Imageflow/internal/ui/runner.go:51)、[app.go:1157](/D:/Code/Imageflow/internal/ui/app.go:1157)。

任务启动时保留行索引，完成时继续用该索引调用 `SetRowStatus`。文件行右键删除和“清空”在处理中仍可执行。互斥锁只防止数据竞争，不能保证删除后索引仍指向同一文件。

触发：处理两张图片时删除第一张。第二张移动到索引 0，随后会收到第一张的完成状态和输出路径。清空后重新导入也可能接收到旧任务结果。

建议：使用稳定的任务行身份及批次代次提交结果；被删除的行应丢弃旧结果。也可以在任务运行期间禁用输入集合变更，并同时约束拖放、导入和清空入口。

证据：独立用例使用通道控制任务完成顺序，稳定复现第二张图片得到第一张输出路径。

### 7. 多尺寸参数无效后 Running 不复位，所有工具无法再次开始

定位：[tools.go:298](/D:/Code/Imageflow/internal/ui/tools.go:298)、[files.go:333](/D:/Code/Imageflow/internal/ui/files.go:333)。

`Start` 在调用工具前将 `Running` 置为 `true`。多尺寸模式解析不到合法尺寸时只设置提示并直接返回，没有调用 `SetRunning(false)`，也没有创建可以完成或取消的任务。

触发：多尺寸输入填写非空无效字符串，然后点击开始。修正参数或切换工具后再次开始，仍然会被运行状态阻止；停止按钮也没有任务令牌可取消。

建议：为工具启动失败建立统一的状态回滚路径，或在占用运行状态前完成参数校验。

证据：独立用例确认参数校验失败后 `IsRunning()` 仍为 `true`。

### 8. 拼图分组丢失原组索引，跳过、失败和取消会改写已完成结果

定位：[collage.go:572](/D:/Code/Imageflow/internal/ui/collage.go:572)、[collage.go:612](/D:/Code/Imageflow/internal/ui/collage.go:612)、[collage.go:629](/D:/Code/Imageflow/internal/ui/collage.go:629)。

`outputs` 只追加成功组，最终却按所有组的 `i/slot` 索引回填。任何跳过都会压缩输出列表，最终回填还会覆盖之前设置的 `skipped` 状态。后续组失败时将所有行标为失败；取消时调用的 `endWholeList` 也会把已经提交文件的组标为取消。

触发：四张图每两张一组，第一组因目标存在而跳过、第二组成功。第一组最终显示成功，并链接到第二组的输出。首组成功后取消后续组，则已存在的成功文件在界面中失去对应的完成结果。

建议：按原组索引保存结果并在每组提交后更新其成员行。结束时只更新尚未完成的组，并按各组实际结果汇总。

证据：独立用例稳定复现“第一组 skipped 被改成 ok，输出指向第二组”。取消和失败分支由静态检查确认。

### 9. 拼图导出 goroutine 直接写界面字段，存在数据竞争

定位：[collage.go:655](/D:/Code/Imageflow/internal/ui/collage.go:655)。

`CollageTool.Run` 在后台完成后直接写 `t.previewKey`。UI 构建和交互处理也会读取、写入这个字符串。`App` 的状态锁没有覆盖工具字段。

触发：拼图导出完成附近继续调整取景、参数或请求预览重绘。可能丢失预览失效通知，且违反 Go 内存模型的并发访问要求。

建议：通过 `Window.Update` 或现有 UI 待处理队列提交预览失效通知；后台任务仅持有请求快照。

证据：独立竞态用例确认 `Run.func1` 的第 655 行与 UI 的 `askRedraw` 第 885 行发生 `WARNING: DATA RACE`。现有全量竞态测试没有覆盖这个交互组合。

### 10. APNG 帧延迟直接转换为 uint16，超过 65.535 秒即回绕

定位：[gif.go:497](/D:/Code/Imageflow/internal/engine/gif.go:497)。

`writeAPNG` 把毫秒延迟直接转换为 `uint16`，分母固定为 1000。GIF 合法延迟可以超过 65.535 秒，降低播放速度也会产生这样的延迟。

触发：将 70 秒的帧导出为 APNG。重新读取后延迟变成 4464 毫秒，动画播放速度错误。

建议：将毫秒约分为 APNG 可表示的分子与分母；不能精确表示时明确规定误差或拆分帧，避免整数回绕。

证据：独立两帧用例确认 `70000ms → 4464ms`。

### 11. PDF“裁切填满”只放大图片，没有裁切到单元格

定位：[pdf.go:157](/D:/Code/Imageflow/internal/engine/pdf.go:157)、[pdf.go:172](/D:/Code/Imageflow/internal/engine/pdf.go:172)。

cover 模式使用较大的缩放比例后直接调用 `doc.Image`，没有设置单元格裁切区域，也没有预先裁切源图。超出单元格的像素仍然进入页面，覆盖其他单元格或页边距。

触发：PDF 选择两栏或网格，再选择“裁切填满”，输入宽高比与单元格差异较大的图片。例如 4:1 横图填入纵向两栏中的一格时，图像宽度将远超单格宽度。

建议：使用 PDF 裁切路径将每张图片限制在自己的单元格，并恢复图形状态；也可预先按单元格比例裁切图片。

证据：静态确认完整绘制链路中没有单元格裁切；未执行 PDF 页面渲染验证。
