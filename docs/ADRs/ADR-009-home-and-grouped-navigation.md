# ADR-009：首页 + 分组侧栏 + 稳定的工具归属

- 状态：已采纳
- 日期：2026-11-17
- 关联：UI-01、UI-02、NFR-06、COMP-02

## 背景

入口从 14 个增长到 25 个之后，出现了三个具体问题：

1. **一列 25 行不再是导航，而是清单。** 用户必须先读完整列才能决定从哪开始；首屏把"基础编辑""AI 高清放大""转 PDF"混在同一竖列里，没有任何层次。
2. **冷启动落在某个工具上是一种误导。** 启动即打开「格式转换」，等于替用户假定了任务。
3. **没有检索入口。** 用户知道自己要"改大小""打码""压缩"，但不知道该点哪一行。

## 决策

### 1. 首页（landing page）

新增首页作为启动视图，包含四块：

- **搜索框**：与侧栏搜索共享同一个 `searchQuery`，按名称 → 前缀 → 关键词 → 摘要分级排序。
- **常用**：固定的 6 个高频任务（压缩、转换、裁剪、拼图、截图美化、调色）。
- **分组清单**：与侧栏相同的分组、相同的顺序、相同的工具卡片。
- **组件状态**：AI 组件是否可用、登记模型数量；未安装时说清"其余工具全部可用"。

### 2. 分组侧栏

- 六个固定分组：基础处理、创作与排版、专业图像、动态与素材、智能增强、历史功能。
- 分组**可折叠**，折叠状态写入 `settings.RailCollapsedGroups`，重启后保留。
- 含当前页面的分组**拒绝折叠**：否则选中指示会指向一个不可见的行。
- 侧栏顶部有搜索框；窄窗口（< 1080 DIP）自动收成图标条，搜索按钮转为"打开首页搜索"。

### 3. 工具归属是固定表，不是方法

`toolGroupOf`（`internal/ui/groups.go`）是唯一的归属声明，`TestEveryToolHasAGroup` 在构建时校验每个页面都有分组与摘要。

## 理由

1. **一个信息架构，两条进入路径。** 首页与侧栏读同一份 `toolGroups`、同一份归属表、同一份搜索逻辑，因此不可能出现"首页说有、侧栏找不到"。
2. **分组不改动用户排列。** 曾经的侧栏顺序是"位置 → 工具索引"的排列；分组只是展示规则，组内顺序仍取自该排列，所以用户拖过的顺序在每个分组里继续生效。
3. **折叠是阅读偏好，不是导航状态。** 它跟"知道这个分组暂时不关心"有关，所以持久化；但它不改变工具身份，也不改变排列。
4. **固定归属表优于 `Tool.Group()` 方法。** 页面实现不必关心导航；归属信息集中在 25 行表里，评审时一眼可见；缺项会被测试抓住。

## 后果

- 拖动换序改为**按可见序号**计算：分组标题不是槽位，跨越标题的拖动等价于"把工具插到另一个工具之前"，落点解析回工具身份后再重写排列（`commitRailDrag`）。
- 选中指示的 y 来自行表本身，不再用"索引 × 行距"：标题行与分组间距打破了固定节奏。
- `TestRailGroupsFoldAndKeepTheActivePageVisible`、`TestRailSearchRanksExactNamesFirst`、`TestHomeListsEveryToolOnce`、`TestEveryToolHasAGroup` 固定上述不变量。
- 侧栏搜到的工具被点击后**不清空搜索框**：用户可能在逐个查看匹配项；只有首页卡片跳转才清空。

## 未采纳的方案

| 方案 | 未采纳原因 |
|---|---|
| 保持一列 25 行，只加搜索 | 首屏仍然无法扫读；"常用"与分组提供的是结构，不是过滤 |
| 让用户自定义分组归属 | 归属是产品语义（哪一页属于哪一类），不是偏好；允许改会让"专业图像"这样的分类失去意义 |
| 用最近使用频次生成"常用" | 没有数据时会展示任意六项；固定六项覆盖常见任务，且行为可预期 |
| 分组顺序也允许拖拽 | 分组顺序表达产品层级；允许重排会让"基础处理在最前"这一默认失效，收益不抵复杂度 |
