# Go 原生图片工具箱：功能扩展与技术开发规范

> **版本**：v1.0（技术调研与实施方案）  
> **日期**：2026-11-16  
> **适用对象**：Go 后端/桌面端开发者、前端设计与测试人员  
> **文件性质**：基于现有功能截图与公开开源项目的**增量开发规格**，不是对当前项目源码的审计。真实代码结构、当前 Go 版本、GUI 框架和已实现子功能，须在立项前核对。

## 0. 执行摘要和最终建议

本项目的目标不是重造 Photoshop，也不是添加所有图片相关功能，而是提供一个**启动快、空闲资源占用低、图片处理稳定、功能入口清晰、离线优先**的桌面图片工具箱。

**最终产品导航**确定为：①基础处理；②创作与排版；③专业图像；④动态与素材；⑤智能增强。保留原有的「批量水印」等工具内多文件处理能力，但**不建设独立批量管理中心**。

**本次明确不开发**：OCR、文字识别、文档扫描、纸张校正、可搜索 PDF、PDF 合并拆分及其他文档类新功能；CLI、CSS Sprite、Base64、开发者资源集等开发者工具；独立批量管理、相册整理、去重和文件监控等图片管理功能。截图里现存的「转 PDF」视为**历史功能**：不新增功能、不参与本轮迭代，可在产品侧决定保留旧入口或归到“其他/已有功能”，但此规范不要求移除已有可用代码。

**技术战略**：

1. 基础图像操作优先采用 Go 标准库及纯 Go 库；把图像编解码、图像操作、颜色与元数据、动图、外部推理分别封装。不要因个别格式或 AI 功能，让常规任务强制依赖 CGO、Python、FFmpeg、libvips。
2. 对于 JPEG/PNG/GIF 等普通文件，以 Go 处理为默认路径；对于 AVIF/HEIC/JXL、视频解码、真正的 AI 超分辨率，采用**可选适配器**，若找不到可靠纯 Go 实现，宁愿标为“不支持/可选安装”，也不隐式调用不明程序。
3. **Upscayl 兼容增强**采取“Go 原生 UI/调度 + 独立 NCNN/Vulkan 推理二进制”的方案。Electron 的资源占用可以通过去掉 Electron 框架层降低，但**AI 推理速度主要由模型、GPU、驱动、NCNN 版本、tile 和线程参数决定，不能仅因主程序改用 Go 就保证提速**。
4. 在许可证允许且满足兼容需求的情况下，优先评估 MIT 授权的 Real-ESRGAN-ncnn-vulkan，而不是直接将 AGPL-3.0 的 Upscayl/upscayl-ncnn 代码并入项目。Upscayl 模型也须逐个核对权重许可。

## 1. 现有能力基线与范围控制

根据截图，现有入口共 14 项：**格式转换、尺寸调整、图片裁剪、宫格切图、图片布局、图片拼图、长图拼接、批量水印、色彩提取、图标生成、转 PDF、GIF 工具、富文本制图、图片压缩**。

以下表格只描述**应当补充的子能力**，不表示当前软件完全没有这些能力；如已实现，则按验收用例检查并跳过。

| 现有入口 | 本轮重点增强 | 优先级 | 边界 |
|---|---|---|---|
| 格式转换 | 编解码能力探测、透明度、色彩配置、EXIF 旋正、文件大小预测 | P0 | 超出可靠 Go 能力的格式分级支持 |
| 尺寸调整 | Fit/Fill/Pad、插值算法、宽高锁、禁止放大、DPI 信息处理 | P0 | 不使用 AI 冒充传统缩放 |
| 图片裁剪 | 比例、旋转、任意角、自动去边、预览一致性 | P0 | 主体识别属可选 AI |
| 宫格切图 | 自定义行列、分割间距、切割线预览、自动命名 | P1 | 不扩展成图片管理功能 |
| 图片布局 | 自由画布、吸附、层级、蒙版、画布模板 | P1 | 不做 PSD/复杂矢量设计器 |
| 图片拼图 | 自适应网格、模板、自动填充、图片间距 | P1 | 与自由布局共用渲染内核 |
| 长图拼接 | 横/竖向、宽度统一、截图重叠去重、手动对齐 | P1 | 自动拼接失败时可手工修正 |
| 批量水印 | 九宫定位、平铺、混合、水印变量和透明度 | P0 | 仅此功能的多文件入口，不建批处理中心 |
| 色彩提取 | K 主色、色块占比、取色、颜色空间转换、对比度 | P1 | CMYK 为显示转换/参考值，非印前证明 |
| 图标生成 | ICO/Favicon/PWA 资源、多尺寸导出、透明背景 | P1 | 移动应用资源按用户指定标准导出 |
| 转 PDF | 暂不新增 | **冻结** | 文档类功能不纳入本规划 |
| GIF 工具 | 帧、时序、调色板、压缩、反转、动图互转 | P0/P1 | 视频互转需可选解码器 |
| 富文本制图 | 画布/字体/背景/高亮/导出倍率 | P1 | 仅作为“文字图片创作”，不做文档解析 |
| 图片压缩 | 目标体积、画质模式、编码器能力表、对比预览 | P0 | 编码器按真实支持声明，不承诺全格式 |

### 1.1 四个边界判据

- **属于图片编辑**：直接编辑、组合、渲染、分析或生成可视图像。例如文本卡片、海报、GIF、色彩曲线。
- **属于文档处理，排除**：OCR、纸张定位、扫描件透视、PDF 内部页处理、表格识别；虽然用户截图已有“转 PDF”，不继续扩展。
- **属于文件管理，排除**：相似文件查找、整理相册、批量重命名、文件夹巡检、通用操作流水线。但原有水印、转换等工具允许处理多个输入文件。
- **属于开发者工具，排除**：CLI、API、Base64、Sprite、CSS 输出、工程资源集生成。

### 2.2 通用工具页面

统一“导入区域—参数面板—结果预览—导出区”的四段结构。打开后先显示源图；处理参数修改时优先基于**低分辨率预览**计算，最终导出重新以原始图为输入运行完整参数。

**标准交互**：拖入或粘贴图片 → 读取图片基础信息（像素、帧数、格式、透明度、ICC）→ 更改参数 → 左右滑动对比 → 导出新文件或复制图片。对大于预览阈值的图片进行缩略图渲染，绝不因用户拖动滑块而每帧重新解码 8K 原图。

**所有编辑工具至少具有**：撤销/重做、恢复默认、适应窗口、1:1 原图、缩放与平移、透明棋盘格、自定义导出命名、覆盖警示、错误提示。批量水印、GIF 多帧编辑等页面可以增加必要的对象/帧列表，但不要建立跨工具任务管理系统。

**组件复用**：图片布局、拼图、截图美化共享 `CanvasScene`；调色/滤镜/基础编辑共享 `ImageOperation`；GIF、APNG、动态 WebP 共享 `FrameSequence`；AI 推理单独隔离。

## 3. 基础处理：细化规格

### B01 格式转换（P0）

- 输入：至少 JPEG、PNG、BMP、GIF（静图/首帧需显式提示）、WebP（如安装解码器）；TIFF、APNG、HEIC 等按编解码能力表决定，不依据文件扩展名盲目承诺。
- 输出：JPEG、PNG 为必需；GIF、BMP、WebP、TIFF 等视实现验证。颜色模式：RGB/RGBA，透明图转 JPEG 时强制提供背景色（默认白色且可改）。
- 含动画的输入选择“保留动画 / 提取首帧 / 全部帧”选项，静态格式不能悄悄丢帧。
- 色彩：预览显示是否包含 ICC；复制元数据和清除元数据互斥；优先正确转换到 sRGB 再编码，不能通过直接删除非 sRGB ICC 来假装色彩正确。
- 验收：透明 PNG→JPEG 背景正确；带 EXIF Orientation 6 的 JPEG 不会重复旋转；GIF→PNG 会明确“只保存第 N 帧”。

### B02 尺寸调整（P0）

- 模式：按像素、百分比、目标长边/短边；Fit（完整包含）、Fill（裁切铺满）、Pad（留白铺满）；锁定宽高比默认开启。
- 插值：Nearest（像素图）、Bilinear（速度优先）、Catmull-Rom/Mitchell（均衡）、Lanczos（质量优先）；滤镜说明只描述特性，不预设唯一最优。
- 处理 EXIF 方向后计算宽高；输出像素总量超限时先拦截；独立提供“允许放大”开关；DPI 仅修改打印元信息时不得造成意外重采样。
- 验收：1000×500 → 400×400 Fit 结果 400×200；Fill 结果 400×400；Pad 结果 400×400 且内容不裁失。

### B03 图片裁剪（P0）

- 自由裁剪、常用比例、输入精确 X/Y/W/H、保持或解锁比率、画布外区域填充、左/右 90° 旋转、水平垂直翻转。
- 自动去边：扫描边缘连通颜色或 alpha，设置容差和安全留白；对实拍照片的近色边缘要允许取消自动结果。
- 任意角旋转采用逆向采样；明确扩展画布与保持画布两种行为；图片导出时必须保证坐标和预览一致。

### B04 图片压缩（P0，建议核心差异化）

- **三种主模式**：高画质（默认推荐）、小体积、指定文件大小；高级面板显示格式、质量、色度采样（若编码器支持）、分辨率上限、是否剔除元数据。
- 指定文件大小采取**质量二分搜索 + 必要时分辨率逐级下降**。因编码参数非严格单调、压缩耗时不同，应设置最大尝试次数和允许误差（默认 ±5%）；不可达时提供最接近结果，不宣称一定满足。
- JPEG、PNG、WebP 等不同格式应显示不同参数。透明 PNG 用无损/调色板量化模式，不给用户一个无意义的“JPEG 质量”滑块。
- 可视化：输出大小、缩减百分比、当前质量、耗时、100% 放大前后滑动对比；可选 PSNR/SSIM，注明对比参考图和指标局限。
- **绝不默认覆盖原图**；如果处理后文件更大，提示“文件反而变大”，给出保留原文件或继续导出的选择。
- 回归用例：照片、动漫、截图、中文文字、透明 Logo、纯色渐变、噪点图；比较边缘光晕、色带、透明边缘黑边和颜色漂移。

### B05 基础图片编辑（新增，P0）

整合旋转、翻转、画布扩展、背景填充、边框、圆角、阴影、模糊、锐化、灰度、反色、局部像素化等基本操作。这里不做图层历史文件格式，不与“专业调色”重复建立第二套色彩引擎。

## 4. 创作与排版：细化规格

### C01 宫格切图（P1）

自定义 1–20 行、1–20 列（阈值需由 UI 限制）、列/行独立间隔、画布适配和切割线预览；支持按“从左到右、从上到下”编号。切图统一使用整数边界分配，最后一格自动吸收整除余数，**不丢像素、不重叠**。单张输出或 ZIP 打包为工具导出形式，不创建独立文件管理页。

### C02 图片布局（P1）

自由画布 + 图层基本模型：图像、文字、形状、背景。支持拖放、对齐吸附、等距分布、前后层级、裁切蒙版、圆角、阴影、透明度；预设仅保存在当前功能中。输出最大像素数受内存预算限制；大画布可按条带分段合成。

### C03 图片拼图（P1）

照片拖入后自动产生 2–9 张常见拼图方案：规则网格、错落布局、拍立得、横竖分栏。格内默认等比填充（Fill），支持每格拖动改变取景；可定义外边距、格间距、背景和角半径。布局能力调用 C02 的共享渲染核心，但拼图界面侧重“快速出图”。

### C04 长图拼接（P1）

横向/纵向手工拼接、统一宽度或统一高度、顺序拖动、相邻图对齐。新增滚动截图的**自动重叠匹配**：先降采样，限制搜索区域，使用边缘/亮度归一化相关性寻找重叠，给出置信度；低置信度时必须展示两图接缝并允许手动输入偏移。防止重复导航栏、悬浮按钮和纯白区域造成误匹配。

### C05 批量水印（P0，保留现有范围）

- 水印：文字、PNG Logo、平铺、固定九宫点位；透明度、角度、比例、边距、描边/阴影。
- 变量：`{filename}`、`{date}`、`{index}`，仅作为此工具内置功能，不扩展为通用重命名软件。
- 对色彩管理后的图像进行 alpha 混合；编辑预览时显示水印安全区，批量处理按图片自身分辨率缩放水印尺寸。
- 明确：可见水印是辅助版权标记，不保证不可被删除；本产品不承诺水印去除/对抗功能。

### C06 富文本制图（P1，严格限制在图片创作）

支持文字片段、标题、副标题、代码高亮、引用块、卡片背景、字体/字重/行高、文字折行、Emoji 字体回退、图片边距和多倍率 PNG 导出。内部可以接受简化 Markdown 作为排版输入，但**不提供 Word/PDF 文档导入、OCR 或文档版面解析**。

### C07 图片标注（新增 P0）

箭头、矩形、圆、自由笔、编号圆点、文本框、局部高亮、模糊和马赛克。对于“永久隐私遮盖”，须提供**直接以不透明纯色覆盖并导出重编码文件**的独立模式，避免把轻微模糊/马赛克误当成可靠的敏感信息删除方案；保留的 EXIF 元数据依用户隐私选项处理。

### C08 截图美化（新增 P1）

支持已有截图拖入、美化背景、圆角、阴影、内外边距、边框、玻璃背景效果（最终输出为静态图像）、常用横竖比例导出。若实现系统截图，应在 Windows 使用 OS API，并与编辑器解耦；**系统全屏录屏不是本轮功能**。

## 5. 专业图像：细化规格

### P01 图片调色（P1）

- 基础：曝光（EV）、亮度、对比度、高光、阴影、饱和度、自然饱和度、色温、色调、Gamma、白平衡。
- 进阶：RGB 曲线、色阶、HSL 分色、通道混合、分离色调、LUT（`.cube`，先支持常见 3D LUT 结构和三线性插值）。
- 计算规则：涉及曝光、混合、模糊等的操作，优先在线性光或明确的工作色彩空间执行，避免简单在 sRGB gamma 编码值上累加造成偏色；对仅 8-bit 的路径明确告知潜在色带问题。
- **非破坏性**：记录参数而非多次重编码；预览可降采样，导出时从原图重新计算；修改参数支持 200–400 ms 防抖或取消旧任务。

### P02 图片滤镜（P1）

灰度、复古/棕褐、胶片曲线、颗粒、暗角、浮雕、边缘检测、素描、像素化、卡通化（非 AI 的颜色量化 + 边缘组合）、基础模糊/锐化；提供滤镜强度和参数详情。自定义 LUT 如测试稳定再开放。注意“漫画/油画”等名称应符合真实算法效果，不用营销词掩盖简单阈值滤波。

### P03 图片对比（P0）

原图/结果图分屏、滑杆、叠加、闪烁；同步缩放/平移；局部坐标的 RGB/Alpha 显示；像素差异热图、绝对差和 SSIM/PSNR（先统一两张图尺寸和色彩空间，必要时明确“对齐方式”）。压缩、放大、调色、矢量化各工具都可以调用该组件，无须独立创建对比副本。

### P04 图像分析（P1）

RGB/亮度直方图、Alpha 统计、色彩数量估计、主色占比、亮度过曝/欠曝分布、像素取样、边缘强度和位深/ICC/方向标志展示。大图采用采样统计或分块累积；所有百分比注明采样/全量模式。

### P05 位图转 SVG（P2）

纯 Go 第一版仅做**高对比二值图形的轮廓追踪**：阈值 → 连通域 → 轮廓提取 → 多边形简化 → 贝塞尔拟合 → 写出 SVG。彩色插画高质量矢量化难度高，可选用 VTracer 等独立二进制做高级模式，严禁把“PNG 封装进 SVG”冒充矢量化。

**不在本轮**：RAW 全流程、CMYK 印前软打样、Photoshop PSD 图层完全兼容、HDR 专业色彩管理（有需求可另立项）。

## 6. 动态与素材：细化规格

### M01 GIF 与动画工具（P0/P1）

帧列表、拆帧/合帧、删除/复制/重排、逐帧时长、整体变速、倒放、循环次数、帧透明度和背景混合、文字覆盖、裁剪、缩放、导出优化；支持 GIF 到静态帧，以及 GIF/APNG/动态 WebP 在**可用编解码器**之间互转。视频→GIF 属可选 FFmpeg 扩展，不进入基本安装包。

**关键实现**：GIF 帧常为增量矩形，必须正确处理 `disposal`（恢复背景/恢复前一帧等），导出前合成完整画面再进行颜色量化；不要简单地把 `gif.GIF.Image[i]` 当作完整的独立画面。帧时长采用对应格式的单位，避免将 GIF 百分之一秒、APNG 分数时基混淆。

调色板质量：内置基础 median-cut/Octree/NeuQuant（经基准验证选择）、有序或误差扩散抖动；要求纯色文字边缘不出现明显脏点。帧间差分压缩在第二阶段加入。

### M02 图标生成（P1）

ICO 的 16/24/32/48/64/128/256 尺寸集合、网站 Favicon、PWA/移动端常用 PNG 组合；自动缩放时支持“安全区”和透明边缘预览。ICO 封装若 Go 库成熟度不足，可按 ICO 文件结构用 Go 生成 PNG-compressed entry，且必须做 Windows Explorer 真实显示验证。

### M03 色彩提取（P1）

点取色（HEX/RGB/HSL/HSV）、主色提取（如 K-means + 采样/聚类排序）、颜色占比、互补/近似/三色方案、渐变条生成、WCAG 对比度计算。避免默认对透明像素参与取色；配色结果要注明“由输入像素统计得出”，不是色彩校准仪测量结果。

### M04 视频帧提取（P2，按需安装 FFmpeg）

选视频文件 → 读取时间/时长 → 指定时间点、时间间隔、抽帧 FPS → 生成 JPG/PNG；提供缩略时间轴和每段预览，支持生成 3×3 故事板。视频解码、封装与硬解是独立复杂领域，纯 Go 不应在本项目中从零重写 H.264/H.265/AV1 解码器；使用外部 FFmpeg 前检查许可证、可执行文件来源和安全参数。

### M05 像素画与电子纸点阵图（P1）

- 固定调色板：2/4/8/16 色、Game Boy 风格、灰阶与**1-bit 纯黑白**。
- 抖动：None、Bayer Ordered、Floyd–Steinberg、Atkinson；所有算法在 Go 实现并提供算法与强度说明。
- 支持目标尺寸、近邻放大、像素网格预览、边缘增强、色彩阈值与反色；提供例如 400×300 像素的用户自定义预设。
- 黑白模式承诺输出每像素严格只有黑/白，不会偷偷引入灰色抗锯齿；若生成 JPEG 会丢失严格 1-bit 语义，建议用 PNG/BMP。

### M06 表情包制作（P1）

静态/动态图片加字、字边描线、漫画气泡、上下字幕、头像圆形贴图、常用比例、GIF 帧上叠加、社交平台文件大小/尺寸限制（由用户选模板，不依赖实时网络规则）。与富文本制图共用文字排版，与动图工具共用帧处理。

### M07 背景素材生成器（P2）

纯 Go 程序生成线性/径向渐变、网格、棋盘、条纹、圆点、噪声纹理、几何图案、抽象背景。可以提供随机种子重复生成，默认输出高质量 PNG。不要引入在线 AI 生图服务作为必需依赖。

## 7. 智能增强与 Upscayl：专项技术评估

### 7.1 调研结论（已核对源码）

- 官方 `upscayl/upscayl` 主程序的 `package.json` 显示：它使用 **Electron + Next.js/TypeScript**。在其 `electron/utils/spawn-upscayl.ts` 中，Electron 使用 `child_process.spawn` 启动独立可执行程序；`get-arguments.ts` 负责组合 `-i/-o/-m/-n/-s/-g/-f/-w/-c/-t/-x` 等参数。
- 核心 `upscayl/upscayl-ncnn` 是基于 NCNN、Vulkan、Real-ESRGAN 的独立推理实现；主程序和此后端均采用 **AGPL-3.0**。
- 上游 `xinntao/Real-ESRGAN-ncnn-vulkan` 使用 **MIT**，提供 `-i/-o/-s/-t/-m/-n/-g/-j/-x/-f` 等常见参数，但**它并不保证支持 Upscayl fork 独有的 `-w/-c` 行为，不能机械复用全部命令参数**。
- 官方 Upscayl FAQ 要求 Vulkan 兼容 GPU；本地纯 CPU 不属于官方 Upscayl 同等性能的默认路线。NCNN 框架本身支持 CPU，不代表 Upscayl 的特定 CLI 必然提供可用 CPU 回退。
- Upscayl 默认模型列表包括 standard、lite、high-fidelity、remacri、ultramix-balanced、ultrasharp、digital-art 等 4× 模型。定制模型通常由 `.param` 与 `.bin` 配对组成；不能假设所有模型都支持任意倍率。官方在部分非原生倍率下采用后处理缩放。

**重要判断**：使用 Go 重写 Electron UI 与调度组件可以减少应用常驻框架开销；相同推理二进制、相同模型和 GPU 下，**AI 推理时间基本不由宿主 UI 语言决定**。真正优化应集中在：图片不重复解码、正确设置 tile、保持推理进程最少初始化、输出写盘路径、预览缓存、内存释放与取消语义。

### 7.2 建议实施路线

| 路线 | 实现方式 | 优点 | 风险 | 推荐 |
|---|---|---|---|---|
| A：MIT 基础方案 | Go 调度 + **Real-ESRGAN-ncnn-vulkan** 独立程序 + 合规模型 | 许可证相对宽松；无 Electron；隔离故障；易升级 | Upscayl 模型/扩展参数兼容性须逐个验证 | **默认** |
| B：精确兼容 Upscayl | Go 调度 + `upscayl-ncnn` AGPL 二进制 | 特定 Upscayl 模型/参数更接近原客户端 | AGPL 合规、二进制和权重分发复杂；不能凭进程分离断言免责 | **法律审查后可选** |
| C：完全 Go 实现 AI 推理 | 在 Go 中重写 NCNN/Vulkan 模型执行 | 语言层统一 | 工作量大、性能与兼容性风险高 | **不推荐** |
| D：CPU 备用方案 | 独立模型推理运行时（如经验证的 NCNN CPU/其他原生组件） | 无独显设备可用 | 速度/质量差异大，需另配模型 | **远期可选** |

**许可证特别注意**：AGPL/GPL 与模型权重通常是不同的合规对象；把 AGPL 组件包装成“外部 exe”不自动消除许可证义务。应检查整个应用的分发、程序之间的耦合、源代码改动和相应源码提供要求。这里是工程风险提示，不构成法律意见。若希望保持闭源或宽松许可，默认使用路线 A，并对模型权重各自确认分发许可。

### 7.3 超分辨率 UI 规格

- 输入图片、原图宽高、图像类别（照片/插画/动漫）、模型、目标倍率、输出尺寸、存储目录。
- 预览：按 256×256 或 512×512 局部区域先运行局部增强，保证用户可比较纹理与边缘；注意局部推理上下文不足时与整图效果可能不完全一致。
- 高级选项：GPU 设备（如存在多个）、tile（auto/128/256/512 等；实际限制按运行时）、TTA（高耗时）、输出 PNG/WebP（仅当该引擎版本支持）、保留可保留的元数据。
- 设备检测：先检查推理二进制版本、模型文件完整性，再进行试运行；无 Vulkan/驱动异常时显示用户可理解的错误和兼容性说明。
- 模型管理：内置最少一个合规可分发模型或让用户手动导入；导入时检查 `.param/.bin` 配对、大小、哈希、倍率元数据、模型架构兼容性及来源。第三方模型信息需要 `model.json` 显式声明，不靠文件名字符串推断。
- 任务：运行/取消/重新执行；错误退出保留诊断日志；临时文件失败即清理；成功后原子改名为正式文件；源图绝不覆盖。

### 7.5 Go 引擎抽象及最低可行实现

```go
// 业务层不依赖具体 NCNN CLI；命令行差异由 adapter 处理。
type UpscaleRequest struct {
    InputPath, OutputPath, ModelID string
    NativeScale int   // 模型实际倍率，例如 4
    TargetWidth int   // 可选：在独立 Go resize 阶段达到最终尺寸
    GPUIndex int      // -1 = auto
    Tile int          // 0 = auto
    TTA bool
}

type UpscaleEngine interface {
    Name() string
    Probe(ctx context.Context) (EngineCapabilities, error)
    Upscale(ctx context.Context, req UpscaleRequest, onProgress func(Progress)) error
}

// 使用 exec.CommandContext(ctx, verifiedAbsoluteExePath, args...)；
// 绝不通过 cmd /c 或 sh -c 拼接用户文件名；
// 对模型路径、输入路径、输出路径做白名单及归一化；
// CLI 参数按已检测的引擎版本分别生成；
// stderr/stdout 只作为进度提示，最终以退出码 + 输出文件校验判断成功。
```

推荐进程运行：`UI → Go Service → UpscaleEngine Adapter → 受信任的 NCNN 可执行文件 → 临时输出 → Go 校验和原子提交`。Go 侧通过 `context.Context` 取消任务；Windows 子进程及派生进程清理应进行真实测试，避免取消后 GPU 仍运行。

**与原客户端性能的对比方法**：使用相同模型、输入图、推理引擎、GPU、驱动、tile、TTA 和输出格式，在分别冷启动与热运行条件下测试：A) 空闲 RSS / 私有工作集；B) UI 首次可操作耗时；C) 单张推理端到端耗时；D) GPU 显存峰值；E) 10 次重复运行中位数与 P95；F) 结果图片像素/感知指标。切勿只对比 Electron 进程的内存和 Go 主进程的内存而漏掉 NCNN 推理子进程。

### 7.6 其他 AI 能力（非核心、延后）

智能抠图可以通过可选 NCNN/ONNX 原生推理适配器实现，优先人物与普通商品背景分割。去模糊、对象擦除、旧照片修复是**不同任务**，不得直接把 Upscayl 的超分辨率结果宣传成对应修复能力。任何新模型须满足许可证、设备检测、单独下载和可卸载。

## 8. Go 原生优先：技术选型与取舍

### 8.1 Go 库候选清单

| 能力 | Go 优先实现 | 是否纯 Go | 成熟度判断与注意事项 | 最终建议 |
|---|---|---|---|---|
| JPEG/PNG/GIF 基础编解码 | `image/jpeg`、`image/png`、`image/gif` | 是 | 标准库稳定，GIF 动画帧须正确处理 disposal | **基线必用** |
| BMP/TIFF/WebP 解码 | `golang.org/x/image/{bmp,tiff,webp}` | 是 | `x/image/webp` 主要是解码，不能当作 WebP 通用编码器 | **默认解码** |
| 缩放、旋转、裁剪 | `github.com/disintegration/imaging`、`golang.org/x/image/draw` | 是 | `imaging` 功能清楚、成熟；其读取/输出元数据和色彩管理能力有限 | **基础模块** |
| 滤镜链、卷积、阈值、锐化 | `github.com/disintegration/gift` | 是 | 提供多种 filter，可组合但要合理安排拷贝与并发 | **专业滤镜模块** |
| 多种图像操作、直方图 | `github.com/anthonynsimon/bild` | 是 | MIT、带并行算法与纯 Go WebP 编码；当前主线要求 Go 1.25+ | **候选验证** |
| 彩色/动画编解码与 ICC | `github.com/kovidgoyal/imaging` | 核心功能宣称纯 Go | MIT；支持动画 WebP/APNG、ICC v2/v4、EXIF；**要求 Go 1.26**，部分未支持格式会自动回退 ImageMagick，必须测试关闭回退 | **优先 PoC，暂不锁定** |
| APNG 动画 | `github.com/kettek/apng` | 是 | 可编解码，作者提示 encoder 测试不够充分；高风险用例需自建测试集 | **备选** |
| 文字排版/画布合成 | Go 标准库 `image/draw`、`golang.org/x/image/font`，辅助 `gg` 或项目内部场景渲染 | 是 | 文字 shaping、CJK 字体、emoji/复杂脚本不等同于简单 TTF 绘制 | **自建薄层+小依赖** |
| 颜色分析、直方图、抖动、K-means | 自建 Go 算法 | 是 | 算法简单且可控，优先实现并单测 | **原生** |
| ICO 文件封装 | 自建 Go writer 或验证现成 Go 库 | 可以 | 验证 PNG 嵌入、多尺寸与 Windows Explorer 兼容 | **原生优先** |
| 简易 SVG 生成 | `encoding/xml` / 模板安全写入 SVG | 是 | 适合轮廓与几何图形，不意味着有完整复杂 SVG 渲染器 | **原生** |
| 复杂彩色矢量化 | VTracer（Rust）独立进程 | 否 | 确认分发许可证与跨平台版本；只装高级功能时需要 | **P2 可选** |
| 视频解码 | FFmpeg 独立进程 | 否 | 不建议纯 Go 从零实现复杂视频 codec | **P2 可选** |
| AI 超分辨率 | Real-ESRGAN-ncnn-vulkan 独立进程 | 否，C++/Vulkan | 主应用保持 Go；GPU 推理不是 Go 标准库适合重造的能力 | **首选 AI 后端** |
| 高性能大图流水线 | libvips / govips（CGO） | 否 | 部署复杂，只有大量基准证明必要时再启用 | **不是默认依赖** |

**推荐对标的两个 Go 实现组**：

- **保守稳妥版**：标准库 + `disintegration/imaging` + `gift` + `x/image` + 自建动画/颜色封装。优点是构建可控、迁移成本低；劣势是现代格式、ICC 和动画 WebP 仍要补不少能力。
- **激进纯 Go 版（实验分支）**：重点评估 `kovidgoyal/imaging` 的 ICC、EXIF、APNG、动态 WebP 与动画接口，和现有图片处理逻辑并行进行 PoC。它的 README 表明是 `disintegration/imaging` 的新 fork，但这不等于已经在目标环境完成性能和兼容性验证。切换之前必须完成 Go 版本升级、跨平台构建与回归测试；禁止不同库对同一张图片隐式重复转换颜色配置。

**统一 Go 版本**：先读取现有仓库 `go.mod`；若当前低于 Go 1.26，可以继续沿用稳定组合，不应为了单个候选库强迫立刻升级。升级需要重新测试桌面打包、CGO 依赖、Windows ARM64/AMD64 等目标平台。

### 8.2 编解码能力矩阵（产品应动态展示）

这里的“候选”并不代表当前软件已支持；发布前需要给每个实际启用的引擎打勾，并由测试确认。读写方向须分开列。

| 格式 | Go 读取 | Go 写入 | 动画 | 决策 |
|---|---|---|---|---|
| JPEG/JPG | 标准库 | 标准库 | 否 | P0 必选 |
| PNG | 标准库 | 标准库 | 普通 PNG 不含动画 | P0 必选 |
| GIF | 标准库 | 标准库 | `DecodeAll`/`EncodeAll` | P0 必选 |
| BMP | `x/image/bmp` | 标准 `image` 无内建 BMP encoder；需用对应 Go 实现 | 否 | P1 |
| TIFF | `x/image/tiff` | 选用包支持编码，但需测色彩和位深 | 多页 TIFF 不在本轮 | P1 |
| WebP | `x/image/webp` 解码；或候选库 | `bild` / `nativewebp` 或候选库 | 动态 WebP 需独立验证 | P0 读 / P1 写 |
| APNG | `kettek/apng` 或新候选库 | 同左 | 是 | P1 |
| ICO | 需单独解析/取尺寸 | 可纯 Go 实现多尺寸封装 | 否 | P1 |
| SVG | 仅具备 SVG 光栅化适配器时可读 | 可生成有限 SVG 路径 | 不做脚本/外部资源支持 | P2 |
| AVIF / HEIC / JXL | 不假定标准库支持 | 不假定标准库支持 | 各格式另行论证 | P2；按需可选 codec |

格式转换 UI 的“支持列表”必须来自运行时 `CodecRegistry.Capabilities()`，而非手写一个永远显示所有格式的下拉框。尤其是静态 PNG 和 APNG、静态 WebP 与动态 WebP 必须分开标明能力。

### 8.3 色彩空间与像素类型

标准作业路径建议为：`源文件 → Magic Bytes 探测 → 头信息和像素上限校验 → 读取颜色/方向/帧信息 → 规范化内部表示 → 操作 → 输出色彩策略 → 编码/原子保存`。

- 8-bit `image.NRGBA` 适合常用绘图，但在图层混合和色彩曲线中可能反复损失精度；专业调色应保留更高精度的中间表示（`RGBA64` 或 float 工作缓冲），**只在最终编码阶段量化**。
- `RGBA`、`NRGBA` 的 Alpha 预乘语义不同；合成时统一约定，防止半透明边缘发黑。
- 非 sRGB 图像要依据真实 ICC 做转换；如当前库无法准确转换，提供“保留源 profile 并警告”或“暂不支持精准颜色”的明示处理，而不是无声丢弃 ICC。
- 旋转、裁剪、组合后，EXIF Orientation 应更新/归一为 1，以免其他软件再次旋转。
- 无法正确继承的元数据要在导出界面标明“保留可支持项目 / 清除 / 仅保留版权信息”，不能承诺完整无损保留所有 EXIF/IPTC/XMP。

### 8.4 GUI 与桌面应用形态

Go 原生计算内核不意味着必须重写目前前端，也不意味着 UI 必须用 Go widgets 绘制。

- **保留当前 GUI**：如果当前界面已经稳定，优先重构后端处理内核，在产品功能完整后再评估换壳。这是风险最小的方式。
- **Wails（Go + 系统 WebView）**：适合继续使用 HTML/React 一类界面，Windows 使用 WebView2，不需要打包整套 Electron Chromium。它仍然属于 WebView UI，并非完全原生控件；实际内存包含 WebView2 子进程。Wails v3 当前文档标注 Go 1.26+，应先核对项目构建链和平台支持。
- **Fyne / Windows 原生绑定**：更接近 Go 控制 UI，适合工具面板，但对于复杂画布、手势、富文本和动图预览，需要更多自行研发与测试。

**推荐**：以 Go Core 为核心，UI 薄层为外围。用户提出“原生 Go”，应具体落到**核心计算、任务调度和常用编解码路径纯 Go**，不要仅用“Wails/Go”标签暗示整套应用没有 WebView、C 库或子进程。

### 9.1 必须先冻结的核心数据结构

```go
// 各功能与 GUI 共享的数据结构（示意，不绑定具体包名）。
type ImageInfo struct {
    Width, Height int
    FrameCount int
    Format string
    BitDepth int
    HasAlpha bool
    HasICC bool
    Orientation int
}

type CodecCapability struct {
    Format string
    CanDecode, CanEncode bool
    CanDecodeAnimation, CanEncodeAnimation bool
    SupportsAlpha bool
    SupportsICC bool
}

type ImageOperation interface {
    ID() string
    Validate(info ImageInfo) error
    Apply(ctx context.Context, src image.Image) (image.Image, error)
}

type ExportOptions struct {
    Format string
    Quality int
    StripMetadata bool
    Background color.NRGBA
    AllowOverwrite bool
}
```

注意：示例接口是为静态图设计；**动画处理需独立 `FrameSequence` 接口**，对帧时长、合成方式和循环次数进行显式处理。不要用 `[]image.Image` 丢失动画语义。

### 9.2 编辑会话的非破坏性模型

保存 `SourceRef + OperationList + CurrentIndex + PreviewState`；参数调整时更新操作描述，不覆盖源文件。撤销/重做通过调整操作列表或历史快照实现，不保存每次 8K 全图。导出时重新读取源文件并按顺序执行操作。

由于用户明确不需要独立批量管理，这一 `OperationList` **只服务于当前一张图片的编辑会话**，不能默默扩成跨目录批处理编排器。

### 9.3 文件和内存策略

- `DecodeConfig` 或等效头读取在完整解码前执行，检查文件字节上限、像素总量、动画帧数和预计内存。
- 对 4K、8K 等大图使用预览图缓存，预览层 LRU 按**字节数**预算，不只按图片张数。
- Go `image.Image` 默认未必实现分块懒加载；在纯 Go 原型中，对大图使用显式整图内存预算和分段输出。若某操作依赖完整图，提前预估 `W × H × bytesPerPixel × 同时存在的缓冲数`。
- 不限制 `GOMAXPROCS` 为固定机器值；提供“节能/均衡/性能”线程选择，任务内并发不得导致 CPU 大量超售。
- 出口写入同目录临时文件（例如 `.tmp-<random>`），完整写入、`Sync`（如适用）、关闭、有效性检查后再 `Rename`；Windows 上目标已存在/原子替换行为需按平台具体处理。
- 路径处理用 `filepath`，不要假定 Linux 斜线；避免目录穿越、后缀伪装和临时目录被其他用户篡改。

## 10. 性能预算、优化方案与测量方法

### 10.1 性能目标是“待测验收门槛”，不是现有实测数据

建议搭建两级测试平台：A. Windows 11、8 GB 内存、普通核显；B. Windows 11、16 GB 内存、中档独显。原则上优先 Windows 桌面；跨平台仅在实际产品支持时纳入同等验收。

| 测试场景 | 初始目标（待测、可按产品实际调整） | 如何测量 |
|---|---|---|
| 冷启动至可操作 | 非 AI 基础包 ≤ 2 秒（普通 SSD） | 关闭进程、冷启动 20 次取 P50/P95 |
| 空闲内存 | 不载入图片后尽量低，目标主进程+UI 组件 P50 ≤ 120 MB | Windows 私有工作集、计入所有辅助进程；先测基线再冻结 |
| 2000×1500 图片常规预览 | 首次预览 ≤ 500 ms（B 平台） | 排除文件选择器时间，包含真实解码/缩放 |
| 滤镜参数响应 | 预览计算响应目标 ≤ 150 ms，重任务可延迟且可取消 | 低清预览、持续滑动测试 |
| 4K JPEG 图片处理 | 不触发显著磁盘交换且不冻结 UI | 峰值 RSS、分配量、GC pause、CPU |
| PNG/GIF 动图导出 | 导出后帧时间、循环、透明区域符合期望 | 像素 diff、帧序列断言 |
| AI 增强 | 对同版本 NCNN 实现不低于宿主方式的端到端水平 | 同配置 A/B；记录显存及完整子进程 RSS |

这些指标不是对每种硬件的保证，正式版本应记录测试机器配置、输入数据集、引擎版本和测试脚本。尤其不要给出“Go 比 Electron 快 X 倍”的笼统结论，除非同等测试条件下测量得到。

### 10.2 Benchmark 基线矩阵

测试图片集合建议固定保存 SHA256：

| 数据集 | 典型内容 | 重点故障 |
|---|---|---|
| JPEG-Photo | 12 MP / 24 MP 摄影图片 | EXIF 方向、颜色、重采样、压缩质量 |
| PNG-Alpha | 2048×2048 半透明 Logo | alpha 黑边、透明合成 |
| Screenshot | 2560×1440 中文 UI 截图 | 文字锐度、渐变色带 |
| Anime | 1920×1080 动漫/插画 | 平涂压缩、边缘光晕、超分伪影 |
| GIF-Motion | 30/120 帧，含局部帧/还原背景 | disposal、帧延时、抖动、透明 |
| APNG/WebP-Motion | 小帧区域 + 不同帧率 | 混合/循环与帧精度 |
| Huge | 8K 与超宽长图 | 内存 OOM、导出耗时、取消 |
| Corrupt | 假扩展名、截断和超大头、解压炸弹 | 不崩溃、错误分类、安全限制 |
| ICC | Display P3 / AdobeRGB / 带 EXIF Orientation | 色彩正确性、重复旋转 |

**性能报告至少包含**：`耗时 P50/P95、最大 RSS、总分配字节、GC 次数及暂停、CPU 时间、输出体积、画质指标、测试 SHA、程序 commit`。基准环境固定 Go 版本与平台电源模式，禁止在性能测试中同时运行 GPU 密集任务。

### 10.3 该优化什么、不该优化什么

- **先消除重复工作**：重复解码、重复缩放、每次 slider 变化做全图处理、无效 NRGBA↔RGBA 复制、导出前重复读取文件。
- **优先限制峰值**：图片解码常占几十到数百 MB，额外一份 `RGBA64`、多个滤镜中间层很容易叠加；有必要时引入 buffer pool，并在测试中证明不会长时间持有巨型缓冲。
- **可选 SIMD/CGO**：只有 benchmark 显示 Go 路径不能接受，再对瓶颈局部提供加速后端；不要整套改为 CGO 而失去部署优势。
- **AI 的 GPU 显存问题不是 Go GC 能解决的**：需要 tile 自动策略、引擎进程关闭、输入输出大小估计以及驱动错误处理。

## 11. 错误处理、安全和兼容性要求

1. **文件格式以魔数和有效解码结果为准**，扩展名仅作为提示；无论文件是否来自网络下载，都按不可信输入处理。
2. **限制资源开销**：硬性设置最大像素、最大帧数、最大允许临时文件体积和预览缓存预算；动画文件需检查 `宽 × 高 × 帧数` 的总工作集，而不只是压缩文件体积。
3. **操作可取消**：长时间滤镜计算每条带/每帧检查 `ctx.Done()`；GPU 子进程必须确保无残留；失败不产生伪成功结果。
4. **用户隐私**：默认纯离线；不得未经告知把用户图上传到远程 AI；定位 EXIF 采取明确选择，提供清除隐私元数据选项。
5. **图片标注的隐私遮盖**：打码不能保证无法复原，永久敏感信息删除必须使用不透明覆盖后重新编码，导出前删去不必要的元数据。
6. **文字资源与字体**：不得随意打包有分发限制的商业字体；中文、emoji 和复杂脚本做字体回退和缺字警告。
7. **外部程序与模型**：二进制存放在受信任的只读位置，进行 SHA256 校验，不能执行用户输入的任意路径或 shell 字符串；模型下载必须有可信来源和校验信息。
8. **可诊断性**：错误码按 `UNSUPPORTED_CODEC / CORRUPT_IMAGE / TOO_LARGE / OUT_OF_MEMORY / INVALID_COLOR_PROFILE / GPU_UNAVAILABLE / MODEL_MISSING / ENGINE_FAILED / CANCELLED / PERMISSION_DENIED` 分类。UI 显示简短中文说明，详细日志只存在本地且默认不记录敏感完整文件路径到外发诊断。
9. **发布兼容**：目标 Windows x64；若要支持 ARM64、macOS、Linux，逐项验证编解码、文件关联、Vulkan/Metal/驱动、外部二进制以及打包/签名。不要因为 Go 代码可交叉编译就宣称整个功能在所有平台可用。
10. **依赖许可**：每次构建生成 SBOM、`THIRD_PARTY_NOTICES.md`；AI 权重的许可证、来源、修改权和再分发权独立审查。

## 14. 给执行开发 Agent 的工作原则

**允许自由确定内部包名和 GUI 组件细节，但不得变更已经明确的范围排除项。** 按 M0→M5 顺序拆任务，每一个功能必须交付：界面状态、参数验证、纯 Go 默认实现或明确的 adapter、测试样本、性能记录、异常处理、依赖与许可证说明。每次合入前写一份简短 ADR，说明为什么采用该库、为何不纯 Go，以及它是否进入基础安装包。

本规范的核心完成标准不是“导航菜单增加了多少图标”，而是：**常用功能快速可靠、调色与动图不出错、AI 可选且合规、离线即可完成绝大部分任务、普通使用不需要安装臃肿的原生套件。**
